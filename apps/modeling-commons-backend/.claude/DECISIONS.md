# Decisions

## Entity ids: NanoID instead of UUID

All entity ids switched from `crypto.randomUUID()` to NanoID, generated by `newId()` and validated by `idSchema()` in `src/shared/utils/id.ts`.

- 21 characters, default NanoID alphabet `A-Za-z0-9_-`. Collision probability is negligible at this project's scale, and the alphabet is safe unescaped in URL segments, S3 keys, and JSON.
- Hard cutover, no transitional dual-accept window: generation and validation switched together. The project is pre-beta, so a shock is acceptable and a permissive "accept both shapes" period would only leave a pattern lying around that something eventually starts depending on.
- Two deliberate exceptions remain UUID-shaped, each carrying an explaining comment at the source:
  - `src/shared/utils/validate-request-id.ts` still accepts inbound UUID `x-correlation-id` / `request-id` headers, for interop with upstream proxies and tracing systems that generate UUIDs.
  - `storagePathHash` in `prisma/legacy-migration/lib/file-keys.ts` is a frozen UUID-shaped hash of a legacy integer id, pinned by test. It is deterministic on purpose; changing its output would orphan existing S3 objects.

Full rationale and inventory: `doc/nanoid-id-migration-plan.md`.

## 2026-10-16 — Comments and notifications use nanoid ids; the worker stays in the API process

**Context:** `apps/modeling-commons-backend`. After the rebase onto app/modeling-commons, every comment route returned 400: `Model.id` had become a nanoid (d017fb41) while the comment module still validated `:id` as `format: 'uuid'`. The same run exposed two unrelated e2e problems: a preview fixture that fails byte sniffing, and a dev server whose event processor raced the test harness on the shared database. Plan in `.ongoing/post-rebase-e2e-fixes/`.

**Decisions:**
1. **`ModelComment`, `UserNotification` and `UserNotificationPreference` ids are nanoids.** Prisma defaults moved to `@default(nanoid())` (client-side, no SQL diff) and the comment domain generates with `newId()`. Every param and DTO in both modules uses `idSchema()`; `format: 'uuid'` no longer appears in `src/`. No data migration: pre-beta, no production rows.
2. **The event processor is not split into a separate container or process.** It stays inside the API process via `startWorkers(fastify)`. The protection against a second worker sharing the e2e database is a harness guard (`single-worker-guard-4.md`, proposed), not a deployment change.
3. **Validation `subErrors` are a JSON string.** The wire schema already declares `subErrors` as a string; the handler now `JSON.stringify`s the `[{ path, message }]` list instead of letting the serializer coerce it to `[object Object]`. Keeping the string type avoids a client change.
4. **The preview fixture is a real 1x1 PNG**, because `resolveFile` decides on sniffed bytes only. Test fixtures must be what they claim to be.
